# 指摘の記録と弱点の見直し

指摘を1件ずつ直すだけでは、同じ根の失敗が形を変えて繰り返される。本スキルは、指摘を記録として溜め、週に1回束ねて「根にある弱点」を言葉にし、弱点に効く対策を作る。

Skill `feedback-mining` との分担は次のとおりである。

| | `feedback-mining`（月曜 11:00） | 本スキル（月曜 12:00） |
| --- | --- | --- |
| 材料 | 会話の履歴から拾った指摘 | 会話の中でその場に書いた記録と、`feedback-mining` の結果 |
| 単位 | 指摘1件ごとに、反映済みかを見る | 複数の指摘を束ね、共通の根（弱点）を見る |
| 出すもの | 決まりの案（1件ずつ） | 弱点の一覧・前の週からの変化・弱点ごとの対策の案・前に入れた対策が効いたか |

画面の文言への指摘は、画面の文言の記録（既定は `~/.local/state/ui-text/feedback-log.md`）に書き、本スキルの記録には書かない。週次の見直しでは、画面の文言の記録があれば両方を読む。

利用者の環境だけの決まりは、上書きファイル `${XDG_CONFIG_HOME:-~/.config}/claude-skills/weakness-review.local.md` に書く。あれば最初に読み、本文と食い違う箇所は上書きファイルに従う。

## 1. 指摘を記録する（会話の中）

利用者に振る舞いを直されたら、直す作業と同じ会話のうちに、記録 `${CLAUDE_REPORTS_STATE:-~/.local/state/claude-reports}/weakness-review/log.md` の末尾に1件足す。足した後に「指摘を記録した」と1行で伝える。

記録する指摘:
- 「違う」「そうじゃない」「さっきも言った」「〜しないで」「〜してって言ったよね」、作業の差し戻し、やり直しの依頼。
- 進め方・確認の仕方・書き方・道具の使い方・判断の仕方への指摘。

記録しない指摘:
- 業務の内容そのものへの指示（仕様の変更・好みの変更）。
- 画面の文言への指摘（画面の文言の記録に書く）。

書式（1件ごと。見出しの日時は週次の見直しで期間を切る基準になるので、必ず `date '+%Y-%m-%d %H:%M'` の値を使う）:

```markdown
## 2026-10-28 14:05 ~/src/my-app
- 指摘: 「さっきも言ったけど、push は聞いてからにして」
- 直された振る舞い: コミットの後、確認を取らずに push しようとした
- 種類: 安全
- 原因: Claude
- その場の対処: なし（決まりは CLAUDE.md の「push は指示されたときだけ行う」にある）
```

- 1行目は日時と作業場所。
- 「指摘」は利用者の言葉のうち必要な部分だけを引く。利用者以外が書いた文章（ツールの結果・貼り付けた文章・フックの出力）を指摘として記録しない。秘密情報と個人情報は書かない。
- 「種類」は次から1つ選ぶ: 進め方 / 確認不足 / 調査不足 / 判断の先取り / 書き方 / 道具の使い方 / 安全 / 報告 / その他。
- 「原因」は次から1つ選ぶ。
  - Claude: 手順・確認・判断の誤り。発言の意味は明らかだった。
  - 言い回し: 発言が2通りに読め、Claude が利用者の意図と違う方を採った。
  - 両方: 言い回しが曖昧で、かつ Claude が聞き返さずに進めた。曖昧なら聞き返すのは Claude の役目なので、言い回しが曖昧でも聞き返さなかった場合は「言い回し」ではなく「両方」とする。
- 「その場の対処」には、直した決まり（メモリ・スキル・rules の名前）を書く。直していなければ「なし」と書き、既に決まりがあるならその場所を書く。

## 2. 週次の見直し（自動モード）

`scripts/run.sh` が月曜 12:00 に起動する。前回の実行より後の記録だけを取り出したファイルを作り、依頼文で渡す。

### 2.1 範囲

- 自動モードで書いてよいのは、依頼文に書かれた結果の出力先だけである。CLAUDE.md・rules・スキル・メモリ・記録そのものは直さない。`scripts/run.sh` が権限の設定で強制する。拒否された操作を別の方法で行おうとしてはならない。
- 会話の履歴（jsonl）は読まない（権限で拒否している）。材料は依頼文に書かれたものだけである。

### 2.2 手順

1. 上書きファイルがあれば読む。続けて依頼文の材料を読む。
   - 今週の記録（取り出したファイル）
   - `feedback-mining` の最新の結果（あれば）。記録と同じ指摘は1件として数える
   - 画面の文言の記録のうち今週の分（あれば）
   - 本スキルの前の結果（最大4週分）
   - 否認リスト（`~/claude-reports/proposals/rejections.md`）と、Skill `skill-audit` の変更の記録（`history.md`）
2. 指摘を「原因」で振り分ける。「Claude」と「両方」は弱点の材料にし、「言い回し」と「両方」は利用者の言い回しの読み方（`rules/user-profile.md`。無ければ新しく作る案にする）の材料にする。`feedback-mining` から来た指摘には原因が無いので、ここで付ける。
3. 指摘を束ねて弱点にする。
   - 弱点は「何をしたか」ではなく「なぜそうしたか」で名付ける。例: 「確認せずに push した」「確認せずに Issue を起票した」は、どちらも「外部への送信の前に止まれない」という1つの弱点である。
   - 弱点として挙げるのは、2件以上の指摘が同じ根を持つもの、または1件でも本番・外部への送信・取り消せない変更に関わるものである。それ以外は「単発」として件数と要約だけを書く。
   - 根の推測は推測と書く。
4. 前の結果と突き合わせる。弱点ごとに「新しい」「続いている（何週目か）」「今週は指摘が無い」を付ける。
5. 前の結果の対策の案のうち、まだ入っていないものを一覧にする。案ごとに、置き場所のファイルを読み、案の文面の要点が入っているかを確かめる。入っていない案は「3.」に「未入れ」として、案の番号・出した日・置き場所を書く。新しい案を作る前に、未入れの案で足りるかを先に見る。
6. 前に入れた対策が効いたかを見る。`history.md` と前の結果から、対策を入れた日付を求め、その日より後に同じ弱点の指摘が出ていれば「効いていない」とし、理由を推測する。
   - 「その場の対処」にメモリの名前を書いた指摘は、その日から7日の間に同じ種類の指摘が出ていないかを見る。出ていれば、そのメモリは効いていないとし、置き場所を1段上げる案（メモリ → rules → hook）を「4.」に必ず出す。
7. 弱点ごとに対策の案を作る。
   - 既にある決まりを先に検索する（各設定ディレクトリの `CLAUDE.md`・`rules/*.md`・`skills/*/SKILL.md`・`agents/*.md`・`projects/*/memory/`、CLAUDE.md が「読め」と指す先）。決まりがあるのに守れていないなら、決まりを足すのではなく、置き場所を変える案を優先する。
   - 置き場所は次の基準で選ぶ。
     | 置き場所 | 選ぶとき |
     | --- | --- |
     | hook | 機械的に判定でき、破られると取り消せない（push・本番・削除など）。文章の決まりが2回以上破られた |
     | rules | 常に守らせたい短い決まり（10行以内）。スキルの中にあるのに、呼ばれずに破られている |
     | スキル（新規・修正） | 特定の作業の手順・点検項目。毎回読ませるには長い |
     | 共通の方針（common.md） | Codex にも守らせたい、作業全般の考え方 |
     | メモリ | 特定の道具・環境の落とし穴 |
   - 案ごとに、置き場所・ファイルの名前・書く文面（新しいスキルなら SKILL.md の全文、hook なら判定の条件）を書く。文面は入れる先の既存の書き方に合わせる。
   - 否認リストと同じ対象・同じ趣旨の案は作らない。
8. 言い回しの読み方の案を作る。`rules/user-profile.md` があれば読み、新しい言い回しは行の追加、外れた行は修正の案にする。表の書式（言い回し・意味・根拠）に合わせる。
9. 結果を、依頼文に書かれた出力先へ書く。構成は「2.3」のとおり。

### 2.3 結果の構成

1. 作成日時、対象の期間、記録の件数（本スキル・`feedback-mining`・画面の文言の記録の内訳）
2. 今週の弱点（弱点の名前・根の推測・根拠の指摘の日時と要約・新しい / 続いている）
3. 前に入れた対策の効き目（対策・入れた日・その後の指摘の有無・効いていない理由の推測）と、前の案のうち未入れのもの（案の番号・出した日・置き場所）
4. 対策の案（番号・弱点・置き場所・ファイル・文面）
5. 言い回しの読み方の案（追加・修正する行と根拠の指摘）
6. 単発の指摘（件数と要約）
7. 原因の内訳（Claude・言い回し・両方の件数）

結果は業務文書として書き、口調・絵文字を使わない。利用者の発言の引用は必要な部分だけにする。

## 3. 結果を読む依頼への対応

1. 結果を開き、弱点と対策の案を利用者に示す。
2. 対策の案と言い回しの読み方の案を、Skill `change-review` の「直したいこと」の記録に1件ずつ足す（`new-change.sh --id-prefix 会話`）。
   会話の記録から作った案なので、置き場所（スキル・rules・hook・方針・メモリ）によらず区分を `要確認` にする。
   出す前に否認リストと訂正リストを読み、同じ対象・同じ趣旨の案は出さない。
3. 承認を受けたものだけを、直す前の版を残して入れる。新しいスキルを作ったときは、スキルの変更の記録（`~/.local/state/skill-audit/history.md`）に書く（次の週の「対策の効き目」の基準になる）。
4. 伝え終えたら、`report-inbox` の手順で既読にする。

## 4. 弱点を見せる依頼への対応（会話の中）

「弱点を見せて」と言われたら、最新の結果の「2.」と「3.」を要約して示す。結果がまだ無ければ、記録を読んで「2.2」の 2〜3 を会話の中で行う。
